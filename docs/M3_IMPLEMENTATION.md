# Applicient — M3 Implementation Checklist

Working checklist for the M3 Tailoring milestone. Check items off as they're done; update the **Status** line at each step when something changes. See [PRD.md](PRD.md) F5 for the requirements this is built from.

**Status:** M3 done, including cover letters and the Answer Pack. §1-§7 all have working, live-verified implementations (backend and a real Composer UI) — CV tailoring, cover letter generation (F5.7), and the Answer Pack (F6.8) all share the same tailor/verify/regenerate pipeline and are each independently live-verified against real data, including the hard gate genuinely catching and fixing real issues on all three. Real, stated gaps remain and are not hidden: HTML/CSS→PDF (§3, LaTeX-only for now — a second renderer stays deferred until requested), only one CV gallery template exists (§3), no true master-CV side-by-side diff beyond the evidence-vs-bullet word-diff view built (§6), self-attested skill evidence embedding covers the top-k scoring path but not a genuinely comprehensive re-index, no browser-driven UI test (no browser tool in this environment, same ceiling as M1/M2).

## Scope

M3 takes one or more scored jobs, grouped by the user into a **job group**, and produces a verified, tailored, exportable CV for that whole group (plus optional cover letter and Answer Pack), via a JSON-delta tailoring step, an adversarial claim-verifier hard gate, LaTeX-first deterministic rendering with a live preview, a template gallery, a skill-gap checklist, and a real Application Composer UI.

**What already exists (M0-era schema, zero application logic):**
- `Document` / `ClaimVerification` models (`models/documents.py`) and `DocumentType` (`cv`/`cover_letter`/`answer_pack`) / `ClaimVerdict` (`supported`/`reframed_ok`/`unsupported`/`inflated`) enums (`models/enums.py:40-45,152-155`) — migrated, never read or written anywhere yet.
- `EvidenceItem.category` already has a `SKILL` value (`models/enums.py:174-188`) and a `verified: bool` column (`models/profile.py:118`) — both fit the skill-gap checklist (§5) directly: a checked-off skill becomes a real `EvidenceItem(category="skill", verified=True, ...)`, no schema addition needed there.
- `retrieve_relevant_evidence` (`scoring_engine.py:194`, top-k=8 cosine nearest-neighbor) is the wrong shape for tailoring, which needs the **full** evidence bank (F5.1) across every job in a group, not a top-k subset scoped to one job. A separate fetch is needed; the existing function stays scoring-only.
- `validate_evidence_spans` (`scoring_engine.py:317`) and the `hard_blocker`-forces-`skip` pattern in `scoring_service.py:161-190` are the precedent for "enforce a model's output in application code, not just in the prompt" — the claim-verifier gate (§4) and the skill-checklist's evidence-only unlock (§5) both follow this.

**Fully greenfield — confirmed by direct inspection, not assumed:**
- No object-storage client anywhere. `pyproject.toml` has no S3 SDK at all. `Profile.raw_cv_object_key` has existed since M0 but is only ever set to `None`.
- `docker-compose.yml` provisions `minio` (healthy, `S3_*` env already in `.env.example`) but nothing writes to it. `api`/`worker`/`browser-worker`/`web` stanzas are still commented out.
- Neither renderer toolchain exists: no Tectonic, no Playwright/weasyprint/pdfkit anywhere. Only `pypdf` is present (for text-layer verification, not rendering).
- `renderers/`, `worker/`, `browser-worker/` are bare empty directories.
- `web/src/app/composer/page.tsx` is a real 13-line placeholder.

**A real schema/PRD mismatch found in this audit, resolved by the redesign below:** `Document.rendered_pdf_key`/`rendered_docx_key` (`models/documents.py:36-37`) don't match F5.2/F5.11's "two PDF renderers, LaTeX first" shape at all — no DOCX anywhere in the PRD, and a fixed pair of columns can't hold a per-template set of renders. Replaced by a `rendered_keys: JSONB` map (`{"latex_pdf": "...", "html_pdf": "..."}`) in §2.

**The job-group pivot (per Adrian's explicit direction — see Log):** a `Document` is generated per `(persona, JobGroup)`, never per single job. A single-job CV is just a group of one — no separate code path for it. Grouping is **manual** for now: the user names a group and assigns scored jobs to it from the Inbox. Auto-suggested clustering by embedding similarity is explicitly deferred, not built here (Adrian's own answer: "manual now, auto-suggest later").

**Renderer sequencing, now LaTeX-first (revised from an earlier draft that had HTML first):** Adrian wants LaTeX→PDF as the primary renderer with a **live preview** in the Composer, so §3 builds Tectonic-backed LaTeX rendering first and proves the live-preview loop before HTML/CSS→PDF is added as a second template family. "Live" is scoped honestly: a debounced re-render on edit/regenerate, not literal keystroke-level typesetting — Tectonic's real compile latency sets the floor here, not a promise.

**Custom template — received, now `renderers/latex_templates/jakes-resume-adrian/resume.tex`** (moved out of the repo root where it arrived). It's a real, complete "Jake's Resume"-style template — `fullpage`/`titlesec`/`fancyhdr`/`roboto`/`soul`, and critically already has `\input{glyphtounicode}` + `\pdfgentounicode=1` wired in, which is exactly what F5.2/§3's "real, ATS-parseable text layer" requirement needs (copy-pasteable text out of the compiled PDF, not glyph-only rendering) — a good sign this template was already built ATS-aware, not something §3 has to retrofit. Structure is macro-driven, not flat text: `\resumeSubheading{title}{dates}{org}{location}` + `\resumeBulletList...End` for experience, `\projectSubheading{name}{dates}{tech}` for projects, `\certItem{issuer}{name}` for certs — §3's per-template registry needs a real delta-fields → these-specific-macros mapping for this template (each template will need its own mapping; that's the actual "config, not code" boundary — the mapping is template-specific config, the render pipeline itself is shared). Header (name/phone/email/links) is currently hardcoded to Adrian's own info — fine for his personal use, but the registry should treat header fields as coming from the profile, not baked into the `.tex` source, if this template is ever offered to more than one profile. Uses `roboto` and `glyphtounicode.sty`, both needing confirmation that Tectonic can actually resolve them (Tectonic normally fetches packages from its bundled CTAN mirror on first use) — a real live-verify item, not assumed, added to §3.

**No separate `worker` service.** Tailoring/verification/rendering run synchronously inside the API process via SSE, the same pattern already used by `cv.py` and `radar.py`. `docker-compose.yml`'s `worker`/`browser-worker` stanzas stay commented out; Redis remains unused.

**CV upload storage backfill, folded into §1:** since M3 needs a real object-storage client anyway (for rendered PDFs), also wire the *existing* CV-upload flow to persist through it, closing the `raw_cv_object_key`-always-`None` gap at near-zero extra cost.

**Explicitly out of scope for M3:** application execution/form-filling (F6, M4), the browser-worker (M4), auto-suggested job-group clustering (deferred per Adrian's answer), any change to Tier 1/2/3 discovery sources.

## 4. Claim verifier (hard gate)

- [x] `claim_verifier.py`: adversarial subagent, `deep` tier, receiving **only** the master profile's full evidence bank + the generated `Document.json_delta`'s own text — never any job posting or the JobGroup (F5.4). Classifies every claim `SUPPORTED`/`REFRAMED_OK`/`UNSUPPORTED`/`INFLATED`, persisted as `ClaimVerification` rows (`attempt_number` capped at 2 per F5.5) via `claim_verification_service.py`.
- [x] Regeneration loop: any `UNSUPPORTED`/`INFLATED` verdict feeds the specific violation back into a second tailoring-agent attempt (`run_tailoring(..., prior_violations=...)`), re-verifies, and sets `Document.verified` from the FINAL attempt's real outcome — never silently forced true. Both attempts' `ClaimVerification` rows are kept for audit history.
- [x] **Live-verified for real, not just the happy path**: a real 2-job group's first tailoring attempt was independently judged by the verifier and caught 3 genuine inflated claims the tailoring model introduced on its own — adding an unverified qualifier ("ensuring reliable and scalable service delivery" not in the evidence), elevating "activities" to "research activities", and inflating the job title from "Associate AI Engineer" to "AI Engineer" in the summary. The regeneration attempt fixed exactly those three issues and passed clean (`verified=True`) on attempt 2. This is real evidence the hard gate works, not assumed from the code.
- [x] Wired into the same SSE stream as tailoring (`POST /job-groups/{id}/tailor`) as a `verifying` stage — extends the stream `POST /job-groups/{id}/tailor` already had rather than requiring a second call.
- **Bug found and fixed along the way**: the tailoring call's structured output (several sections, several bullets, plus a rationale) is long enough to exceed the provider's default max output tokens — a real run truncated mid-JSON. Fixed by binding `max_tokens=8000` on both the tailoring and verification calls (not in `tier_resolution.py`, since this is specific to these two calls' unusually long output, not something every tier-resolved call should inherit). A related prompt bug also surfaced and was fixed: framing every call as "a GROUP of jobs" confused the model for a group of exactly one job, producing sections with zero bullets — reworded to handle 1-or-more postings explicitly, plus an explicit "every included section must have ≥1 bullet" rule.
