## Scope

M0 built the *entire* PRD §9 data model up front, including tables no milestone had touched yet — `Application`, `ApplicationEvent`, `AppliedLedgerEntry`, `EmailMessage`, `Notification`, `AgentRun`/`AgentStep`. That means M4 is not starting from zero schema: `models/pipeline.py` (`Application`, `ApplicationEvent`, `AppliedLedgerEntry`) already exists, with every `ApplicationState`/`AutonomyLevel`/`EventActor` enum value already defined in `enums.py`. What's actually missing is everything *around* that schema: no router, no UI beyond a 12-line "not built yet" placeholder at `/pipeline`, no `FormAnswer` model at all, and zero lines of code anywhere in `browser-worker/` (confirmed — the directory is empty; it's never been scaffolded, not even a `pyproject.toml`).

M4 closes PRD F6 (Application execution) and F7 (Pipeline and tracking), plus one item M2 explicitly deferred here rather than to a named future milestone: `CandidateStatus.NEEDS_GENERIC_SCRAPING`'s own docstring and M2_IMPLEMENTATION.md §5 both say the generic/bespoke career-site scraper for non-ATS companies "remains deferred to M4, where the browser-worker it needs is already being built anyway" — that's a real promise made against this milestone, not a nice-to-have, so it's in scope below (§9).

**Defaults taken for this plan (Adrian wasn't in the room to confirm these live — flag any of them if you want it differently):**

- **`browser-worker/` becomes a real, separate service**, not folded into `api/` the way `worker/`'s planned responsibilities quietly ended up living directly in `api/src/applicient_api/` every milestone so far (radar.py, scoring_service.py, tailoring_service.py, etc. all run in-process today, no actual task queue). That collapse made sense for LLM calls — an `httpx` request has no persistent state and no special resource profile. A Playwright-driven Chromium process is a different animal: it's memory-heavy, it can hang or crash independently of the API process, and F6.6 requires *persistent, disk-backed, encrypted browser contexts per source* that need to survive across requests and ideally across API restarts. That's exactly the isolation PRD §8.1 originally called out browser-worker for, and it's the one place in this codebase where the isolated-service split is still worth its complexity. Communicates with `api/` over a small internal HTTP+WebSocket API, not a shared Python import.
- **`application-agent` is the first real deepagents usage in this codebase.** `agents/src/applicient_agents/setup_verification.py` (M0) proved the mechanism works and was never touched again — every subsequent stage (CV parsing, scoring, tailoring, claim verification, cover letters, Answer Pack) deliberately used a direct LangChain call instead, per `cv_parsing.py`'s own documented reasoning: deepagents' middleware adds real, measured token overhead (~2.5k tokens) that's only worth paying for genuinely open-ended, multi-step, tool-using work. Application execution is the first stage that actually meets that bar — variable-length, needs a todo list, needs real tool calls against a live browser, and needs `interrupt_on` as a first-class primitive (exactly PRD §7.1's own justification for the framework, and exactly what F6.5/F6.7 require). This is the milestone where that criterion finally flips from "no" to "yes," not a default abandoned elsewhere.
- **The exit bar's "real application submitted... with a human at the submit button" is read as L2 (fill-and-review), not L3.** L3 (fill-and-submit under a hard daily cap) is explicit user opt-in per F6.1 and ships behind that cap regardless, but this environment has no way to safely rehearse fully autonomous submission against a real employer's site before Adrian has actually used L2 himself. L3 is built (the state machine and cap don't care which level triggered them) but its own live proof is out of scope for this milestone's verification pass.
- **Verification order for anything that touches a real browser: a disposable, self-hosted test form first, a real job posting only with Adrian's explicit go-ahead.** Every prior milestone's discipline in this repo has been "verify against the real thing, not a mock" — for an LLM call or a public read-only API that's low-risk. Filling and clicking through a real employer's application form is not the same risk class, and this environment can't get informed consent from that employer. The fill-and-review loop gets proven against something disposable and self-controlled before it ever points at a real posting.

**M4 exit bar:** a scored job in the Inbox gets an "Apply" action that creates a real `Application`; at autonomy L2, the application-agent opens the job's real apply form, introspects it via the accessibility tree, resolves every field (form answer memory → profile → generated answers → ask the user), fills it, and stops for a full review (every field, every attachment, a screenshot) before a human clicks submit; a captcha or login wall mid-flow hands off to a live embedded browser view and resumes cleanly afterward; the resulting `Application` and its full audit trail (screenshots, field map, values, errors) are visible on a real Pipeline board (Kanban + table + timeline), which also derives `ghosted` correctly and exports to CSV/JSON.

**Explicitly out of scope for M4:** Gmail ingestion, email classification and state-transition proposals (F8, all of it — M5's job); already-applied ledger CSV/JSON import and Gmail-derived history (F9.1/F9.2 — M6, though the `AppliedLedgerEntry` table already exists from M0 and F9.3's "manual mark-as-applied from any job card" is a natural, cheap addition to wire here as a side effect of building the Pipeline board, so it's called out separately in §10 rather than silently pulled forward wholesale); a bundled captcha-solving provider (F6.10 ships the plugin interface only, disabled, with no real adapter behind it — the point of that requirement is that Applicient itself never solves a captcha); scheduling/cron for anything (F10, M5); the HTML/CSS→PDF renderer and a second CV gallery template (both already-disclosed M3 gaps, unrelated to this milestone).

## 2. `browser-worker/` service scaffold

- [x] New `browser-worker/pyproject.toml` — `playwright`, `fastapi`, `websockets`, `uvicorn`, `python-multipart`. Deliberately **not** dependent on `applicient-api` — the worker is a pure Playwright/HTTP shell with no DB or model access of its own; `object_storage`/`security` access happens on the `api`/`agents` side of the HTTP boundary, in the tools, not inside the worker.
- [x] Real Playwright session manager (`sessions.py`): one shared Chromium process (launched once, `headless=True`), many isolated `BrowserContext`s handed out per session — confirmed live this is Playwright's own recommended multi-tenant pattern, cheaper than a process per session.
- [x] `browser_snapshot` uses Playwright's newer `page.locator("body").aria_snapshot(mode="ai")`, **not** the originally-planned `page.accessibility.snapshot()`/CDP `Accessibility.getFullAXTree`. Real finding during the feasibility check: `page.accessibility` was removed in the installed Playwright version (1.62.0) — it's been deprecated for several releases. `aria_snapshot(mode="ai")` is Playwright's own modern replacement for exactly this agentic use case (the same primitive their own MCP/browser-agent tooling uses): it returns a ref-annotated tree (`[ref=e3]`), and a subsequent `page.locator("aria-ref=e3")` acts on that exact node. Live-verified against a real multi-field test form: fill/click/upload by ref all work and the returned snapshot correctly reflects the new state after each action.
- [ ] `playwright install --with-deps chromium` as a `browser-worker/Dockerfile` build step, and a `docker-compose.yml` service entry — **not done yet**. Development and all live verification this pass ran the worker natively (`uv run browser-worker` on :8100), not containerized; containerizing it is real, bounded, follow-up work, not attempted here given time spent proving the harder mechanism first.
- [ ] Persistent, encrypted auth contexts (F6.6) — **not implemented**. `BrowserContext` (§1) exists as a table but nothing reads or writes `storage_state_key` yet; every attempt today opens a fresh, unauthenticated context. A real, disclosed gap: login-requiring sites will hit `browser_request_handoff` on every single attempt rather than reusing a previously-authenticated session.
- [x] Internal HTTP+WS contract, built as planned: `POST /sessions`, `GET /sessions/{id}/snapshot`, `POST /sessions/{id}/fill`, `POST /sessions/{id}/click`, `POST /sessions/{id}/upload`, `GET /sessions/{id}/screenshot`, `GET /sessions/{id}/storage-state`, `DELETE /sessions/{id}`, plus `GET /sessions/{id}/screencast` (WebSocket, see §5). `agents/src/applicient_agents/browser_tools.py`'s tools are thin `httpx.AsyncClient` calls against this — real HTTP over the wire, not a shared Python import, live-verified via a real end-to-end open→fill→upload→click→screenshot→close sequence against a real Chromium instance.

## 4. `application-agent` (deepagents, tools, interrupts)

- [x] `agents/src/applicient_agents/application_agent.py` — `create_deep_agent` with the real browser tool set (`browser_open`, `browser_snapshot`, `browser_fill`, `browser_click`, `browser_upload`, `browser_screenshot`, `browser_request_handoff`, `submit_application`) plus `form_answer_lookup`/`form_answer_save`/`application_transition` (`agents/src/applicient_agents/browser_tools.py`). - [x] `interrupt_on` wired for the two rows this milestone actually needs: `submit_application` (`allowed_decisions: ["approve", "reject"]`, always at L2) and `browser_request_handoff` (`allowed_decisions: ["respond"]`). - [x] **Fully live-verified, including the mechanism that matters most**: a real LangGraph interrupt on `submit_application` fired with the exact expected payload (`{tool, args: {session_id, ref}, description}`), was approved via `Command(resume={"decisions": [{"type": "approve"}]})`, and the real underlying click executed afterward — confirmed via the tool's own visible follow-up call to `application_transition`, which correctly failed with "application not found" against the verification script's disposable random UUID (proving the approve→execute path ran for real, not a no-op). The same round trip was separately verified for `browser_request_handoff` with a `"respond"` decision. Verified twice: once via a standalone script (`agents/src/applicient_agents/verify_application_agent.py`, kept as a record, mirrors `setup_verification.py`'s own M0 precedent) and once through the real deployed HTTP API (`POST /applications/{id}/apply` → SSE `interrupt` event → `POST /applications/{id}/attempts/{attempt_id}/resume`).
- [x] `AgentRun` used for real (`run_type="application"`); `AgentStep` **not populated** — the SSE stream surfaces agent messages and interrupts directly rather than persisting a step-by-step trace, so Run Console does not yet render an application-agent run the way it renders radar/composer runs. A real, disclosed gap versus the original plan.
- **Real, disclosed model-quality finding, not a mechanism bug**: the account's actual bound `deep`-tier model (`nvidia/nemotron-3-super-120b-a12b:free`) returned a hard 404 ("Provider returned error") on every attempt during this pass, and the `balanced`-tier fallback (`z-ai/glm-5.2:free`) hit a persistent 429 even after its own suggested backoff — both real, live, repeated OpenRouter free-tier outages, confirmed independently of this codebase's own logic. Verification proceeded with a temporary `stage_overrides["application"]` pointing at a different free model (`openrouter/free`), restored to the account's real settings (`{}`) immediately after each verification run — the same "disposable edit to a real row, cleaned up after" discipline this codebase has used since M1. Whatever model ends up bound to `deep` going forward, nothing about the interrupt/tool-calling mechanism itself depends on which one it is.
