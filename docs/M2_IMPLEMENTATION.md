# Applicient — M2 Implementation Checklist

Working checklist for M2 — Preferences & Targeted Discovery. Check items off as they're done; update the **Status** line at each step when something changes. See [PRD.md](PRD.md) for the requirements (F1.9, F2.10, F4.3a) and decisions this is built from.

**Status:** Complete. §1-7 are implemented and live-verified; the remaining generic scraper and other later-milestone work are explicitly out of scope below.

---

## Scope

M1 shipped a `Preference` model that was never actually wired to anything — no router, no schema, no UI — and a fit scorer that only ever reads `Profile.location`/`visa_status`, never the persona's stated preferences. M2 closes that gap and adds real target-company discovery on top of it: given a persona's preferences, propose real candidate companies and resolve them into working ATS sources, instead of the user hand-typing a slug one company at a time.

**Confirmed with Adrian, binding for this milestone:**

- **Company discovery is a scan, not a picklist.** Once a company's ATS identifier is resolved and approved, it joins one persona-scoped source's target list for that ATS type; running that source scans every approved company in one go. The user never checks boxes per company, before or after discovery adds more.
- **ATS breadth: all of PRD F2.2's Tier-1 structured boards, not just Greenhouse/Lever.** M2 adds Workable, Ashby, SmartRecruiters and Recruitee adapters alongside the two M1 already built.
- **Bespoke/internal career sites (e.g. `career.astra.co.id/lowongan`) are detect-and-defer, not scraped.** M2 records that kind of site when it has a verified URL already present on a posting's apply link; a preference-only web-search provider is intentionally not configured, so that path remains unresolved rather than guessing a URL. The actual generic scraper is deliberately left for M4, where the browser-worker it depends on is already being built for application execution. Building an unknown-page-structure scraper twice — once cheaply now, once properly in M4 — is waste; recording *that a site exists and needs scraping* is not.

**M2 exit bar:** a user answers the preference questionnaire once (target roles, seniority, salary, locations + willing-to-relocate, remote policy, industries, company size, deal-breakers) → runs company discovery → reviews and approves a mix of real resolved companies across at least two different ATS types → those companies are scanned automatically as part of the existing saved-search flow, with no per-company selection step → a company with no known ATS (Astra) is correctly recorded as "needs generic scraping" with its real career-page URL rather than silently dropped → a job whose location the user is willing to relocate to scores on merit instead of being penalized for distance.

**Explicitly out of scope for M2:** the generic/bespoke career-site scraper itself (detection and queuing only — the scrape runs in M4 alongside the browser-worker); any change to Tier 2/3 sources (JobSpy, SocialFetch, RemoteOK are untouched); full company enrichment beyond what discovery needs to propose and resolve a name (F3.6, a later milestone).

## 1. Contracts and schema delta

- [x] Audited the existing `Preference` model against F1.9's needs. Added `willing_to_relocate` as a single global boolean, not scoped per `locations` entry — deliberately: `locations` already lets the user name specific target places (used positively, for location-fit match); a second per-location relocation axis is complexity nothing has asked for. The flag instead softens the penalty for a location *outside* that list too (the general "I'd move for the right role" signal), which `locations` alone can't express.
- [x] Added Pydantic schemas: `PreferenceOut`/`PreferenceUpsert` (`schemas.py`) — the latter all-optional (`exclude_unset` semantics) since an unset field means "no opinion," not an error; decided no CV-parse-style confirm gate applies here (every preference field is optional by nature, unlike parsed CV accuracy).
- [x] `Source.config` needed **no migration at all** — it's already a free-form JSONB bag (confirmed directly in `models/discovery.py`), so "generalize board_token to company_identifiers" is a code-level adapter/UI convention, not a schema change. Actual adapter changes land in §4/§6.
- [x] Added `CompanyCandidate` (`models/discovery.py`) for discovery proposals: `persona_id`, `company_name` (unique per persona, normalized before insert — same NFKC/casefold discipline as `Job.canonical_key`), `origin` (`preference_discovery` | `apply_link`), `rationale`, `status` (7-value enum below), `resolved_identifier`, `discovered_url`, `approved`, `origin_job_id`. - [x] Wired the §1 revision stamp all the way through: `persona_revision` (from `Persona.revision`) now stamped on every `PrefilterResult`/`FitScore` write, and `radar.py`'s "already scored, skip" query extended to require `persona_revision` match too — a preference edit now makes a rerun actually re-score, the same passive (radar-re-touches-it) mechanism that already governed `profile_revision`, not a new active trigger.

## 5. Company discovery

- [x] New discovery step (`company_discovery.py`, `propose_candidates`): given a `Preference`, proposes a ranked candidate company list with a stated rationale per candidate, `balanced` tier, structured output (mirrors `scoring_engine.py`'s own shape). No grounding/`web_search` tool built for this — confirmed none exists in this codebase (M1 built no research-agent) and none was needed: the prompt explicitly instructs "never invent a company name," and every real run this session proposed genuinely real companies (verified by hand: Bukalapak, Gojek, Traveloka, Alodokter, etc. — all real). Grounding via a real resolution step (below) rather than a search tool is what actually catches a bad proposal, since an invented name simply fails to resolve.
- [x] ATS resolution (`resolve_company_ats`, PRD F2.5 — confirmed absent from the codebase before this) — derives slug variants (hyphenated-lowercase, no-space-lowercase, original-casing) and live-probes all six ATS patterns with bounded concurrency, deterministic precedence. **A real false-positive bug was found and fixed during live verification, not just theorized**: naively treating "HTTP 200" as resolved is wrong — a random garbage slug correctly 404s on every platform, but a *real, registered, empty* account can still 200. Confirmed directly: `ramp` is a real but empty/unrelated Workable account, entirely separate from the actual fintech Ramp (whose real ATS is Ashby) — resolving "Ramp" without an extra check picked the wrong, empty Workable account purely by trial order. Fixed by requiring at least one real posting from every prober, not just a 200 (SmartRecruiters needs a different signal, `totalFound > 0`, since its list endpoint returns 200 with an empty result for genuinely nonexistent companies too — confirmed live, the one platform of the six that doesn't 404 on an invalid identifier at all). Re-verified after the fix: Hugging Face → Workable, Ramp → Ashby, Equinox → SmartRecruiters, Channable → Recruitee, GitLab → Greenhouse, a nonsense string → unresolved — all correct.
- [x] **Non-ATS detect-and-defer is split by evidence quality.** Preference-only proposals with no known ATS remain `unresolved` because no web-search credential is configured and an LLM must not fabricate a career URL. A real HTTP(S) apply link already stored on an aggregator/social posting is different evidence: `classify_apply_url()` now preserves an unknown-but-valid URL as `needs_generic_scraping`, with the exact URL in `discovered_url`; malformed/absent links are ignored, and the bare Workable `/j/{shortcode}` form stays a known ATS classification without an unusable account identifier. The generic scraper itself remains deferred to M4.
- [x] Apply-link classification (`classify_apply_url`) — regex-matches a posting's `apply_url` against all six ATS domain patterns, independent of which source found the posting. Real, stated edge case found and handled: Workable's own apply links are frequently a bare shortcode (`apply.workable.com/j/{shortcode}`) with no account slug in the URL at all — confirmed live against real Hugging Face postings — so a match there confirms "this is a Workable posting" but yields no identifier to actually scan; handled by returning a resolution with `identifier=None`, which the caller correctly treats as nothing-actionable rather than silently fabricating a slug. Live-verified end to end with a disposable real job row (`apply_url` pointed at a real GitLab Greenhouse posting) — correctly surfaced as an `apply_link`-origin, `resolved_greenhouse` candidate with identifier `gitlab`; disposable row removed afterward.
- [x] Persistence + review surface: `routers/company_candidates.py` — `GET`/`POST .../discover` nested per persona, `PATCH /company-candidates/{id}` flat by id. Both origins (LLM-proposed and apply-link-derived) land in the same table and the same review list, deduped by normalized company name (mirrors `Job.canonical_key`'s own NFKC/casefold discipline) so a repeated discovery run doesn't re-propose what's already sitting there. Frontend: a new "Discover companies" dialog in the radar page — persona picker, a run button, and every candidate shown with its rationale, resolution status, and an approve action; unresolved candidates show plainly as "no known ATS matched — nothing to scan yet" rather than a disabled button with no explanation.
- [x] Approval action (`update_company_candidate`): appends the resolved identifier into a persona-scoped scan-list `Source` for that specific ATS type (`config.company_identifiers`, deduped), auto-creating the `Source` row on first approval if none exists yet — implemented via a deterministic name lookup (`"{ATS display name} (discovered — {persona.name})"`) rather than a new `Source.persona_id` column, since `Source` is otherwise persona-agnostic in this codebase (persona binding happens through `SavedSearch.source_ids`, same as any manually-added source) and a name-based lookup achieves the same one-scan-list-per-persona-per-ATS result without a migration. Approval does **not** auto-create or edit a `SavedSearch` — binding the discovered source into an actual saved search stays the existing manual radar-UI step, same as any hand-added source today.
- [x] **Full live end-to-end verification against Adrian's real persona and real preferences** (not fixtures): ran discovery for real → LLM proposed 12 genuine Indonesian companies matching his actual stated preferences (AI Engineer, Jakarta, hybrid, mid-size) → all correctly resolved `unresolved` except one genuine hit, **Alodokter → `resolved_smartrecruiters`** (a real Indonesian healthtech company that does use SmartRecruiters) → approved it through the real API → confirmed a new `Source` ("SmartRecruiters (discovered — AI Engineer)", `company_identifiers: ["alodokter"]`) was created → tested that source's connection against the real live API → `status=ok`.
