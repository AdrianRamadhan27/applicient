## Scope

M1 is the first thin vertical slice after the foundation: a saved role search fans out to one ATS source and one aggregator, produces canonical jobs with preserved source lineage, deduplicates them, runs cheap prefiltering followed by the full structured fit rubric, and displays an auditable ranked Inbox with per-run cost.

**M1 source choice:** started with a Greenhouse board/API adapter as the ATS source and a JSearch adapter as the aggregator; RemoteOK (free, keyless aggregator) and Lever (a second per-company ATS board) were added after JSearch's RapidAPI subscription turned out to be more friction than expected. All four are behind the same source-adapter contract, so adding/replacing a source does not change normalization, deduplication, scoring, or the UI. Keep all source credentials/configuration in the database-backed source configuration; never put them in agent code or committed environment files.

**M1 exit bar:** a user with a confirmed profile can enter target roles, run the search, see raw-source telemetry and canonical jobs, get ranked structured scores with evidence spans in Job Inbox, see the run's LLM/embedding cost in Cost & Usage, rerun without duplicate jobs, and repeat the run after changing the active provider/model profile from the Models screen.

## 4. Normalization, lineage and deduplication

- [x] Normalize every `RawPosting` into the canonical `Job` shape (`normalization.py`) — NFKC + casefold + whitespace-collapse for the comparison key only, original display values and `raw_posting` payload kept as-is. Adapters already return timezone-aware UTC `datetime`s (`RawPosting.posted_at`), nothing further needed here; absent fields stay null, never invented.
- [x] Salary is pure pass-through — both adapters only ever populate it when the source states it (checked in their own docstrings), so this layer just never overwrites a known `Job` value with an absent one. No market estimate anywhere in the path.
- [x] `Company`/`Job` upsert with every `JobSighting` preserved, `first_seen_at`/`last_seen_at`/`posted_at_on_source` tracked. Live-verified: one real Greenhouse board (GitLab, 202 live postings) → 36 matched jobs, 1 `Company` row, 36 `JobSighting` rows, zero duplicates across 3 reruns.
- [x] Dedup signals 1 (exact `(source_id, external_requisition_id)`, enforced by the real DB unique constraint from §1) and 2 (normalized `canonical_key`) implemented and live-verified idempotent. **Signal 3 (embedding cosine similarity) is NOT implemented** — stated plainly in `normalization.py`'s own module docstring, not silently skipped. In practice this only under-dedups postings that differ in requisition ID/canonical key but are semantically the same job; both M1 adapters always supply a requisition ID, so today's two sources don't hit this gap in practice.
- [x] Bounded-batch embedding of job descriptions through the `embedding` tier (`job_embedding.py`, `BATCH_SIZE=20`), wired into the end of every radar run for jobs it touched that are still missing `description_embedding`. Checkpointing is structural, not a separate table: a failed batch is isolated (caught, recorded, next batch continues) and those jobs simply stay unembedded, so a later call — including signal 3 once it's built — naturally picks them back up without re-charging. An unconfigured `embedding` tier is non-fatal to the run (same discipline as query expansion): the jobs stay real, just unembedded. Live-verified: 3 real jobs from a real Greenhouse run all got real 2048-dim vectors, correct cost/token metering on the `LlmCall` row.
- [x] `apply_url` ATS-over-aggregator preference (`_maybe_prefer_sighting`) — a small preference ranking (`greenhouse` > `jsearch`), re-evaluated on every new sighting, keeping the highest-ranked source's URL. Every source URL stays visible via `JobSighting`, not just the preferred one.
- [x] Ghost/staleness signals (`_compute_ghost_signals` in `normalization.py`): first-seen age (`Job.created_at`) and repost count (incremented when a sighting's `posted_at_on_source` is bumped later without a new requisition ID — a concrete "posted-date reset", not a guess) both feed a scored, reasoned red-flag list, recomputed on every touch to a job. Boilerplate-text detection is explicitly NOT implemented — no objective signal available without risking false positives, stated in the docstring rather than faked. Verified both by unit-testing the scoring function across threshold boundaries and by simulating a real repost through `normalize_and_upsert` twice with the same requisition ID and a later `posted_at` — `repost_count` incremented correctly, `is_new` correctly stayed `False`.

Every model resolved through `resolve_tier`/capability tiers, never named directly.
