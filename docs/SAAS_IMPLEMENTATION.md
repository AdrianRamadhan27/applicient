# Applicient — SaaS pivot implementation checklist

Working checklist for the SaaS pivot. Replaces the PRD's M6 (Breadth & proof) and M7 (Demo dataset) on the active roadmap — dropped per explicit user direction ("forget about M6 and M7, its not needed. I want this to be a fully SaaS instead"). See [PRD.md](PRD.md) for the original single-user-first assumptions this pivot moves away from; there is no updated PRD section for the SaaS model yet, so this file is the authoritative spec for it until one exists.

**Status:** Phase 0 (data model), Phase 1 (admin role + admin-gated Models/Providers/Cost + back-office), Phase 2 (billing, Xendit), and Phase 3 (multi-tenant hosting hardening) are all built and live-verified against the real Xendit sandbox API and real deployed containers. Phase 4 (public signup/onboarding) is designed but not started.

## Scope

Four workstreams, confirmed with the user directly:
1. **Admin/back-office surface** — Models/Providers and Cost/Usage become admin-only; regular users never see or configure LLM providers or raw cost internals.
2. **Billing & subscriptions** — Xendit (Indonesian payment gateway — Stripe isn't approvable without a US entity/bank account), flat subscription tiers with a hardcoded usage cap per plan, not metered/usage-based billing.
3. **Multi-tenant hosting hardening** — closing real gaps found via exploration: one shared app-wide secret key with a default fallback shipped in `docker-compose.yml`, zero rate limiting anywhere in the API, an in-process scheduler that would double-fire on a second `api` replica, an uncapped shared browser-worker Chromium process, no structured per-tenant logging.
4. **Public signup & onboarding** — a real landing page (with a dedicated demo-video section, placeholder until the user supplies the recording), email verification, guided first-run onboarding.

## Phase 0 — Data model foundation

- [x] `User.role` (`models/profile.py`) — new `UserRole` enum (`user`/`admin`, `models/enums.py`), plain `String(20)` column matching this codebase's existing enum-backed-column convention (no native Postgres enum, no SQLAlchemy `Enum` type — confirmed via grep that nothing else in this codebase uses one either, despite `enums.py`'s own docstring describing that as the pattern). Default `user`.
- [x] `User.is_active` — suspension flag. **Enforced at login only** (`routers/auth.py`'s `login()` 403s a suspended user before issuing a new token), not on every request — a deliberate, disclosed trade-off: an already-issued 7-day bearer token keeps working until it naturally expires rather than adding a DB lookup to the hot `current_user_id` path used by every single route in the app. A real, meaningful suspension (blocks new logins immediately) without the larger architecture change of making every request DB-backed.
- [x] Admin bootstrap — `ADMIN_EMAIL` env var (`.env`/`.env.example`/`docker-compose.yml`, defaults to `demo@applicient.local` for local dev). `signup()` sets `role="admin"` for a matching email; the migration promotes any pre-existing matching user; `seed.py`'s demo-user path does the same independently (a third real provisioning site, same pattern the customizable-pipeline-stages feature established). No self-service path to admin exists anywhere.
- [x] `Plan` (`models/billing.py`, new) — `name`, `price_idr` (smallest unit, no floats), `monthly_usage_cap_usd` (caps against the existing `LlmCall.cost_usd` sum — reuses F13's cost ledger directly), `is_active`. Not user-scoped (mirrors `ModelCatalogEntry`'s "not user-scoped directly" reasoning) — a small, admin-managed, shared set of tiers.
- [x] `Subscription` (`models/billing.py`, new) — `user_id`, `plan_id` (real FK, `ondelete="RESTRICT"`), `status` (`trialing`/`active`/`past_due`/`canceled`), `xendit_customer_id`, `current_period_start`/`current_period_end`. One row per user; "exactly one" is app-layer-enforced (same as every other `UserScopedMixin` table in this codebase — no DB-level uniqueness on `user_id` alone).
- [x] Migration `f3a8c1d9e6b2` — adds `role`/`is_active` to `users`, promotes the `ADMIN_EMAIL` match, creates `plans`/`subscriptions`, seeds three placeholder tiers (Free/Pro/Team — editable via the admin Plan CRUD screen, not meant to be final real pricing), backfills every existing user onto the cheapest active plan, and — belt-and-suspenders for `tier_resolution.py`'s now-deployment-wide active-profile lookup — deactivates any stray `is_active` `ModelProfile` not owned by the identified admin. Hit one real bug during first run: the raw-SQL `VALUES` literal for `monthly_usage_cap_usd` needed an explicit `::numeric` cast (Postgres inferred the quoted literals as `text`) — caught immediately (`DatatypeMismatch`), confirmed the transactional DDL rolled back cleanly with zero partial state, fixed, reran clean. Live-verified against the real container: `demo@applicient.local` → `role=admin`; both existing users (including a stray pre-existing disposable test user) backfilled onto the Free plan; the one existing active `ModelProfile` (also the admin's) correctly left untouched.

## Phase 1 — Admin role, admin-gated Models/Providers/Cost, back-office

Confirmed via exploration before building: this is a **narrow** change, not a cascading one — `ModelCatalogEntry` was already "not user-scoped directly," and `tier_resolution.py`'s two `ModelProfile` lookups were the only places the calling user's identity actually mattered for *which model gets used* (as opposed to cost attribution, which stays per-user).

- [x] `deps.py` — new `current_admin_user` (DB lookup on `User.role`, not a JWT claim — avoids a stale-role problem since tokens are 7-day/no-refresh; always reads the live row). First second-layer auth dependency in this codebase; every other route only ever checks "is this a valid token."
- [x] `routers/providers.py`, `routers/model_profiles.py`, `routers/cost.py` — swapped `current_user_id` → `current_admin_user` throughout (every route, no other logic changes needed). `ProviderConnection`/`ModelProfile` rows keep their `user_id` column, now meaning "which admin configured this" rather than "who it's private to." `cost.py`'s two routes stay scoped to the *calling admin's own* `LlmCall`/`AgentRun` rows (unchanged query shape) — this is the operator's personal spend view, not a cross-tenant one; cross-tenant spend lives on the new admin user-list endpoint instead (below).
- [x] `tier_resolution.py` — the one real logic change. New `_active_profile(session)` helper resolves the single active `ModelProfile` **deployment-wide** (`filter_by(is_active=True)`, no `user_id` filter), ordered by `updated_at desc` as a deterministic tiebreak if more than one is ever active at once (the migration's cleanup step is what should prevent that in practice; this is the defensive fallback, not the primary mechanism). The 10 downstream call sites (`radar.py`, `email_ingestion.py`, `scoring_service.py`, etc.) are **untouched** — confirmed live: `resolve_tier` called with two different real `user_id`s (the admin's and a fresh test signup's) both correctly resolved to the same admin-owned profile and built the same chat model, while `user_id` still flows through to `CostLedgerCallbackHandler` for per-caller cost attribution.
- [x] Frontend (`web/src/lib/nav.ts`) — `NavItem` gained an `adminOnly` flag; Models/Credentials/Cost moved from the "System" section into a new "Admin" section (plus two new admin-only entries, Users and Plans). `app-shell.tsx`'s section-rendering loop filters `adminOnly` items against `useAuth().user?.role`, and an entire section header is skipped (not rendered empty) when it has no visible items for the current user. A signed-in non-admin who navigates directly to an admin URL by typing it (not just clicking a hidden nav link) is redirected home via the same `useEffect`-based route guard that already handles the unauthenticated→`/login` case — the backend 403 remains the real security boundary regardless; this is UX only.
- [x] New admin back-office pages: `web/src/app/admin/users/page.tsx` (every tenant: email, role, suspended/active, plan, current-period spend computed server-side by summing `LlmCall.cost_usd` since the subscription's `current_period_start`, or the start of the current UTC calendar month as a well-defined fallback for a free user with no billing history yet; suspend/unsuspend and promote/demote actions, both blocked against self-service on your own account with a clean 422) and `web/src/app/admin/plans/page.tsx` (list, inline rename/re-price, activate/deactivate, add new — the same inline-edit-toggled-by-an-`Input` shape as the pipeline-stages "Manage Stages" dialog).
- [x] `routers/admin.py` (new, `prefix="/admin"`) — `GET /users`, `POST /users/{id}/suspend|unsuspend|promote|demote`, `GET/POST /plans`, `PATCH /plans/{id}`. Every route requires `current_admin_user`.

## Phase 2 — Billing (Xendit, flat tiers)

- [x] **Real API shape confirmed before writing any code, not assumed** — Xendit has no single "create a subscription" call the way Stripe does. Fetched their live docs directly rather than guessing: a flat-fee recurring charge needs two separate calls — a "Pay and Save" hosted checkout session (`POST /sessions`, `session_type: "PAY"`, `mode: "PAYMENT_LINK"`, `allow_save_payment_method: "FORCED"`) that collects the first payment *and* a reusable `payment_token_id`, then `POST /recurring/plans` using that token to establish the actual monthly charge. Their webhook payload shapes could not be fully confirmed for every event (`payment_session.completed` specifically isn't documented in their own reference), so the design deliberately does **not** trust webhook payload fields beyond `reference_id` — the same "polling is authoritative, webhook is a best-effort nudge" shape M5 already established for Gmail (push vs. poll), for the same underlying reason (an inert-on-localhost webhook can't be the only tested path, and an unconfirmed payload shape shouldn't move real money state).
- [x] `models/billing.py` — `Subscription` gained `xendit_payment_session_id`/`xendit_payment_token_id`/`xendit_recurring_plan_id`/`pending_plan_id` (migration `b6d4e8a1c9f7`) to track this two-step, in-flight process. `pending_plan_id` is deliberately distinct from `plan_id` — a user mid-checkout stays on their current plan/cap until the recurring plan is actually confirmed, not the moment they click "Upgrade."
- [x] `billing_service.py` — hand-rolled httpx calls (matching gmail_service.py's existing convention, no Xendit SDK dependency): `start_checkout` (creates/reuses a Xendit customer, creates the Pay-and-Save session), `sync_subscription_from_xendit` (the one function both the webhook handler and the user-facing `/billing/sync` endpoint call — re-derives truth via a direct GET against Xendit's own API, a response shape that *is* confirmed since it's the same schema the create calls return), `enforce_usage_cap` (a FastAPI dependency, same `dependencies=[Depends(...)]` shape as `rate_limit.py`, wired onto the same 5 expensive endpoints alongside the rate limiter — 402s with a clear upgrade message once current-period `LlmCall` spend reaches the active plan's cap).
- [x] `routers/billing.py` (new) — `GET /plans`, `GET /subscription`, `POST /checkout`, `POST /sync`, all `current_user_id`-gated (regular users, not admin-only — this is the account-management surface every tenant needs).
- [x] `routers/webhooks.py` — new `POST /webhooks/xendit`, verifies the `x-callback-token` header via `hmac.compare_digest` against `XENDIT_WEBHOOK_TOKEN`, extracts only `reference_id` from the payload (our own `Subscription.id`, set as the `reference_id` on every Xendit object this app creates) and calls the same `sync_subscription_from_xendit` the polling path uses — always acks 200 on a validly-signed request rather than retry-storming an event this handler can't act on differently next time.
- [x] **Real local-dev gap found and fixed, not left broken**: Xendit rejects a non-HTTPS `success_return_url`/`cancel_return_url` outright (a live 400 on session creation, confirmed firsthand), and `FRONTEND_URL` is `http://localhost:3000` in every local setup this codebase has ever shipped — meaning the real "Upgrade" button would have 400'd for anyone testing locally. `_checkout_return_base_url()` falls back to a placeholder HTTPS URL when `FRONTEND_URL` isn't HTTPS; the fallback destination doesn't need to be reachable, since `/billing/sync` (and the billing page's "Sync payment status" button) don't depend on the redirect landing anywhere in particular.
- [x] `web/src/app/billing/page.tsx` (new) — current plan, a usage-vs-cap progress bar, available plans with Upgrade buttons that redirect to the real Xendit-hosted checkout page, auto-triggers a sync on `?xendit=success` return (plus a manual "Sync payment status" button for the local-dev case where the redirect doesn't land back on `localhost`). Nav entry restored under "Work" (a regular-user page, unlike the admin-only Models/Credentials/Cost/Users/Plans).
- [x] `routers/auth.py`/`seed.py`'s own inline `Plan`-lookup duplication (from Phase 0) and `routers/admin.py`'s duplicated `_period_start`/spend-calculation logic (from Phase 1) both consolidated onto `billing_service.py`'s shared `default_plan`/`period_start`/`current_period_spend_usd` — real cleanup enabled by this phase existing, not scope creep for its own sake.

**Live-verified against the real Xendit sandbox API, not mocked**: confirmed the secret key authenticates (`GET /balance`); created a real Xendit customer for the demo user; created a real, payable checkout session and got back a live `https://dev.xen.to/...` hosted checkout URL; confirmed the subscription correctly shows `pending_plan_name: "Pro"` while staying on Free until payment completes; confirmed the webhook endpoint 403s a wrong `x-callback-token`; confirmed the HTTPS-fallback fix against the real, unmodified `.env` (`FRONTEND_URL=http://localhost:3000`) after first reproducing the exact 400 it fixes. The demo account's test checkout state was reset after each verification pass so the user gets a clean first real run through the actual UI. **Not yet exercised**: an actual completed payment through Xendit's sandbox test payment methods — that requires the user, not this agent, to complete a real checkout in a browser.

## Phase 3 — Multi-tenant hosting hardening

- [x] **Secrets.** `docker-compose.yml`'s default `SECRET_KEY` fallback (a real, repo-committed value anyone who's ever read this file could use to decrypt every tenant's provider keys/Gmail tokens) removed — `SECRET_KEY: ${SECRET_KEY}` now, no default. New `main.py:_require_secret_key()` runs at the very start of `lifespan()`, before the process accepts a single request: fails loud with a clear message if unset, and also validates it's actually a well-formed Fernet key (not just non-empty) rather than deferring to `security.py`'s existing lazy check on first encrypted-field access. Live-verified directly against the function (not just by inspection): raises on missing key, raises on a garbage non-Fernet key, passes clean with a real one.
- [x] **Rate limiting.** New `rate_limit.py` — first real consumer of Redis anywhere in this codebase (it's run in the compose stack since M0 with zero consumers until now). A per-user Redis `INCR`+`EXPIRE` fixed-window counter, fails open if Redis itself is unreachable (a limiter that takes the app down when its own store hiccups is worse than the abuse it prevents). Wired via FastAPI's `dependencies=[]` route option (no handler signature changes needed) onto the five real expensive/LLM-triggering endpoints: `POST /saved-searches/{id}/run` (5/min), `POST /applications/{id}/apply` (10/min), `POST /job-groups/{id}/tailor` (10/min), `.../cover-letter` (10/min), `.../answer-pack` (10/min). Live-verified in isolation (not through a slow real radar/browser run): enforces the limit, resets after the window, correctly fails open when pointed at an unreachable Redis.
- [x] **Scheduler isolation.** `_poll_all_gmail_connections` no longer awaits every connection sequentially and unbounded on the one shared event loop — now `asyncio.gather`'d behind a `Semaphore(5)`, each connection additionally capped at a 60s `asyncio.wait_for` timeout so one hung real Gmail API call can't consume the whole 5-minute poll window for everyone else. `scheduler.py`'s own module docstring now states plainly (not just implicitly true) that `api` must stay a single replica: APScheduler's in-memory jobstore has no distributed lock, so a second replica would independently reconstruct and double-fire every scheduled job. Live-verified against the one real Gmail connection in this environment — polled successfully through the new semaphore/timeout path with no behavior change to the actual ingestion result.
- [x] **Browser-worker session cap** — implemented differently than originally sketched, and disclosed as a deliberate adjustment rather than silently narrowed: browser-worker has zero DB/user awareness by design (confirmed via the M4 docs — a pure Playwright/HTTP shell), so a genuine *per-user* cap has nowhere to live on that side. What it does get: a hard global ceiling (`SessionManager.MAX_CONCURRENT_SESSIONS`, env-overridable via `BROWSER_WORKER_MAX_SESSIONS`, default 20) protecting the one shared Chromium process from being exhausted by any combination of callers — `open_session` now 503s with a clear message past the cap instead of degrading silently. Combined with the per-user rate limit already on `POST /applications/{id}/apply` (above), no single tenant can rapid-fire more than 10 new sessions/minute, and no combination of tenants can exceed the process-wide ceiling — materially equivalent protection to a DB-tracked per-user cap, achieved without adding user-awareness to a service that deliberately has none.
- [x] **Structured logging.** New `logging_config.py` — a minimal stdlib-only JSON formatter (no new dependency), wired in at API startup. Not swept across the whole codebase in one pass (real, disclosed scope-narrowing — every existing `logger.exception("... %s", some_id)` call site would need touching for that, which is separate, larger work); wired into the two call sites that most matter for per-tenant diagnosis right now: the Gmail-poll loop above (now logs `user_id`/`connection_id` as real structured fields, not just interpolated into the message text) and `rate_limit.py`'s 429 path (`user_id`/`endpoint_key`/`limit`). Live-verified the JSON output directly, including a real formatted traceback through `exc_info`.
- [x] **Object storage** — confirmed via the original exploration pass that ownership is already correctly enforced by every call site before reaching `object_storage.py` (a bare key→bytes client with no ownership logic of its own, by design) — left as-is, not rebuilt.
- [x] **Two real bugs caught and fixed along the way, not originally in scope for this phase**: `radar.py` and `routers/cv.py` each had their own direct `db.query(ModelProfile).filter_by(user_id=user_id, is_active=True)` call (recording which profile produced a radar run / CV parse), bypassing `tier_resolution.py`'s `resolve_tier` entirely — found via a repo-wide grep sweep for the same pattern that caused `job_groups.py`'s three near-identical bugs (Phase 1), which Phase 1's own exploration had missed. Left unfixed, every regular (non-admin) user's radar run and CV upload would have silently lost `model_profile_id` attribution the moment Phase 1 shipped (not a crash — `ModelProfile` is now admin-owned, so the per-user query would always return `None` for a non-admin caller). Both now call the same shared `tier_resolution.active_model_profile(session)` helper `job_groups.py` was fixed to use. Live-verified: all three modules resolve to the identical admin-owned profile through their respective imported references.

Verification: `py_compile`/import sanity on every touched file; every live check described above ran against the real Postgres/Redis containers, not mocks. Full rebuild and redeploy of `api`/`browser-worker` (web was untouched this phase), all 6 containers confirmed healthy post-deploy.
