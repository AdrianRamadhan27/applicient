# Applicient — M7 Implementation Checklist

Working checklist for M7 — the Conversational Orchestrator. Not in the original PRD roadmap (M0-M6) — a genuinely new milestone, requested directly: a real, autonomous chat agent that drives Radar (discovery) → grouping → Composer (tailoring) → Pipeline (application execution) end to end, informed by that known-good sequence without being scripted to it. The original PRD §7.2 architecture diagram already envisioned exactly this (a top-level Orchestrator dispatching to named subagents) — M1-M4 each deliberately diverged from it per-stage for real, measured cost reasons; this is the first milestone that actually builds the thing that diagram called for.

**Status:** Built and live-verified end to end against the real deployed stack (real Postgres, real bound model, real containers) — not simulated. A real conversation ran through: an ordinary chat turn, a turn that called real tools (`get_preferences`/`update_preferences`) against a real persona's real data, a full `ask_user` interrupt → resume round trip, and the reject-a-message-while-pending guard. All disposable test data (test conversations, their `AgentRun`/`RunEvent` rows, and the real preference values temporarily changed by testing) was cleaned up/restored afterward. Not yet live-verified: the full guided sequence's later stages (`run_discovery`, `tailor_cv`, `run_application_agent`) — each is a straightforward reuse of an already-independently-verified service (radar.py, the tailoring/verify loop, `start_application_attempt`), but no live run has exercised THIS specific wiring around them yet.

## 1. Data model

- [x] `OrchestratorConversation` (`api/src/applicient_api/models/agents.py`) — the durable, always-alive container for one ongoing chat, one per persona. `AgentRun.conversation_id` (nullable FK) added so each chat *turn* is still an ordinary, bounded `AgentRun(run_type="orchestrator")` — `AgentRun.status`'s existing contract (and everything that already reads it: Run Console, cost aggregation, `reconcile_stale_attempts`'s own stale-run sweep) needed zero special-casing this way, versus leaving one `AgentRun` "running" for a conversation's entire multi-day life.
- [x] Migration `87b74c8441eb` — applied, downgrade/upgrade round-tripped, `alembic check` clean against the real container.
- [x] `langgraph-checkpoint-postgres` added (`agents/pyproject.toml`) — a real, persistent `AsyncPostgresSaver`, not `application_service.py`'s per-attempt `InMemorySaver`: a conversation is meant to span days, so losing it on every API restart would defeat the milestone's own premise. `.setup()` called once at API startup (`main.py`'s lifespan, alongside the existing `reconcile_stale_attempts()`), closed on shutdown.
- [x] `migrations/env.py` — `include_object` filters out `checkpoint*` tables from autogenerate/`alembic check`. Real finding: `AsyncPostgresSaver.setup()` creates and migrates its own `checkpoints`/`checkpoint_blobs`/`checkpoint_writes`/`checkpoint_migrations` tables directly, entirely outside this app's `Base.metadata` — without the filter, `alembic check` sees them as "extra" and proposes dropping them on every future migration. Confirmed clean after the fix.

## 2. Backend tools + agent

- [x] `agents/src/applicient_agents/orchestrator_tools.py` — 13 tools, every one a thin wrapper around an already-existing, already-working service function (never a reimplementation): `get_preferences`/`update_preferences` (`Preference`), `ensure_saved_search` (`SavedSearch`, replicates `routers/radar.py`'s own preconditions since it bypasses that router), `discover_companies` (the `discover_company_candidates` route function, via `asyncio.to_thread` — it calls `asyncio.run()` internally, which raises if awaited directly from a running loop), `run_discovery` (`radar.run_radar_search`, drained fully with human-readable progress emitted per event), `list_top_jobs` (direct `FitScore` query), `create_job_group` (the `create_job_group` route function), `tailor_cv`/`generate_cover_letter_tool` (reproduce `routers/job_groups.py`'s `_tailor_stream`/`_cover_letter_stream` generate → verify → [regenerate → re-verify] sequence exactly, since `tailor_job_group`/`generate_cover_letter` alone don't verify), `create_application_for_job` (the `create_application` route function), `run_application_agent` (`start_application_attempt`, drained only to its first `{interrupt, done, error}` — never re-exposed as this agent's own interrupt), `check_application_attempt_status`, `ask_user` (`interrupt_on`-gated, same contract as `browser_tools.py`'s own).
- [x] `agents/src/applicient_agents/orchestrator_agent.py` — real declarative `subagents=` (deepagents' own `task` dispatch) for `discovery-agent` and `tailoring-agent`, the first real use of subagent dispatch in this codebase (both prior deepagents agents — `application_agent.py`, `setup_verification.py` — are flat). Explicitly **not** used for application execution: `start_application_attempt` already has its own independent lifecycle (own checkpointer, own interrupts meant to be resolved through the existing Pipeline/Live Browser UI, possibly days later) — nesting that compiled graph as a `task` dispatch would either freeze the whole conversation on a pending submit-approval or duplicate Pipeline's own interrupt-resolution UI. `run_application_agent` stays a plain top-level tool instead. Top-level agent's own `tools=` is deliberately a narrow subset (preferences, application, ask_user) — passing the full tool list would give it direct access to `run_discovery`/`tailor_cv` anyway, defeating the whole point of isolating those stages' context into subagents.
- [x] Real, resolved finding on the "how do I disable the auto-added default `general-purpose` subagent" open question: the installed deepagents version (0.7.7) selects it via an internal, per-model "harness profile" (`_harness_profile_for_model`), not a `create_deep_agent(...)` kwarg a caller can set directly — confirmed by reading the installed package. Left in place deliberately (documented in `orchestrator_agent.py`'s own module docstring) rather than fought — harmless extra surface given `discovery-agent`/`tailoring-agent` already have clear, specific descriptions.
- [x] Stage names, all resolved only via `tier_resolution.resolve_tier`: `orchestrator` (top-level, tier `deep`), `orchestrator.discovery-agent` / `orchestrator.tailoring-agent` (tier `balanced`) — dotted-substage convention matching the existing `application.form_answer_lookup` precedent.

## 3. Conversation driver + endpoints

- [x] `agents/src/applicient_agents/orchestrator_service.py` — `send_message` (an ordinary new chat turn, `astream({"messages": [...]})`) and `resume_message` (resolves a pending `ask_user` interrupt, `astream(Command(resume={"decisions": [...]}))`), both funneling through `_drive_turn`. Real, new mechanism: `run_discovery`/`tailor_cv` etc. can take minutes — `emit_progress` writes each intermediate event as a durable `RunEvent` *and* pushes it onto an `asyncio.Queue`; `_drive_turn` fans in the agent's own `astream()` iterator and that queue concurrently (`asyncio.wait(..., return_when=FIRST_COMPLETED)`) so a human watching the chat sees live progress from inside a long tool call, not silence until it returns. Only a thin per-conversation `asyncio.Lock` is kept in memory (reject a second concurrent turn against the same conversation) — no `_ACTIVE_ATTEMPTS`-style registry is needed, since the persistent checkpointer already carries everything a restart would otherwise lose.
- [x] `api/src/applicient_api/routers/orchestrator.py` — `POST /orchestrator/conversations` (idempotent per persona, same precedent as `create_application`), `GET /orchestrator/conversations[/{id}]`, `POST .../messages` and `POST .../resume` (both `EventSourceResponse`, same convention as `routers/applications.py`), `GET .../events` (full replay, not incremental — a conversation spans many `AgentRun` rows so `RunEvent`'s per-run `seq` isn't a valid cross-conversation cursor; ordered by `created_at` instead, and the total event volume is nowhere near what motivated incremental replay for radar). Registered in `main.py`.

## Open risks (carried from the plan, not resolved here)

1. **Long-run token cost** — the top-level thread accumulates a summary per stage forever, since a conversation is meant to persist for days. No archival policy (e.g. auto-`status="archived"` + a fresh thread once an `Application` is created) exists yet.
2. **Tailoring/cover-letter/apply are real spend triggered by the model's own judgment**, guarded today only by a system-prompt instruction to confirm first (soft, not a hard `interrupt_on` gate like `submit_application`'s own). Worth a real gate if this turns out to be too loose in practice.
3. **Abandoned conversations mid-tailoring or mid-apply** — nothing times out a turn stuck at `pending_interrupt` or an in-flight tool call today; no `reconcile_stale_attempts`-style sweep exists for orchestrator turns.
